Issue Description & Problem Statement

When Stripe sends retry events for charge.succeeded or invoice.payment_succeeded during network timeouts, our payment service occasionally creates duplicate credit ledger transactions. This caused 14 customers to receive double credits during last week's upstream Stripe webhook delivery spike.

Technical Root Cause:

The webhook handler in src/webhooks/stripe.ts processes the event payload immediately before committing the idempotency lock. If two webhooks for the same event_id arrive in parallel within a 200ms window, both pass the preliminary DB check.

Architectural Solution Rationale

Formulated by Antigravity (Gemini 3) via AST Index

Strategy Chosen: Distributed DB-Level Unique Lock with In-Transaction Rollback

Instead of relying solely on in-memory Node cache or application-level locks (which fail across multi-pod Kubernetes replicas), the agent will introduce an atomic idempotency_keys record inside a Postgres transaction.

  1. Step 1: Intercept webhook before business logic begins.
  2. Step 2: Attempt INSERT INTO idempotency_keys (key, event_id, status) VALUES (...) ON CONFLICT (key) DO NOTHING.
  3. Step 3: If row already exists with status COMPLETED, short-circuit immediately with HTTP 200 and return cached response payload.
  4. Step 4: If row insertion succeeds, execute credit transaction, then update idempotency key status to COMPLETED within same database unit-of-work.
